# Network Validator local service

The local Compose stack runs `cmd/networkvalidator`'s continuous challenge loop (ADR-011/013): identity/lifecycle, the round-driven challenge-and-evidence loop against assigned providers, and closing rounds once quorum is reached. One instance, `networkvalidator`, is part of the *default* stack; two more, `networkvalidator-2` and `networkvalidator-3`, are the opt-in `multi-node` profile -- see the README's "Multi-provider, multi-validator local network" section. This file covers the operational and trust-boundary detail that section doesn't.

## Why the default stack includes one, and why one is not enough

Before this change, `cmd/networkvalidator` was a real, tested binary with no Compose service running it at all -- the local "network" had no committee actually challenging providers or closing rounds. A single default `networkvalidator` instance makes that loop observable (it registers, goes `ACTIVE`, discovers providers, and submits evidence), but `pallet-network-validator`'s `MinQuorum` is 3 (`blockchain/runtime/src/lib.rs`): `close_round` dispatches successfully at the RPC layer even below quorum, but fails inside the runtime as a silent no-op (see `blockchainbridge.Registrar.CloseRound`'s doc comment) -- so a round never actually closes, and no aggregate ever reaches `pallet-reputation`, with only one validator running. Enable `COMPOSE_PROFILES=multi-node` to run all three and see rounds actually close.

## Image and entrypoint

`networkvalidator` has no dedicated Dockerfile: it builds from `control-plane/Dockerfile`, the same image `control-plane` itself uses (that Dockerfile now builds three binaries -- `control-plane`, `controlplane-admin`, `networkvalidator` -- into one image, mirroring how `controlplane-admin` already shipped alongside the server). The Compose service overrides only `entrypoint`/`command` to run `/usr/local/bin/networkvalidator run` instead of the default `control-plane` server process.

## Identity and mTLS

Each validator instance's signing key (`deployments/local/validators/validator-key.pem`, `validator-2-key.pem`, `validator-3-key.pem`) is an Ed25519 PKCS#8 key generated by `deployments/scripts/generate-dev-certs.sh`, mounted read-only at `/run/openinfra-validator/`. Unlike the Provider Agent's and Control Plane's TLS certificates, this key is never CA-signed and needs no CSR step: it is one identity for two purposes -- signing this validator's own chain extrinsics directly (never sudo-wrapped, never sharing the Control Plane's bridge account) and, self-signed, its mTLS client certificate when it dials a Provider Agent's `SolveChallenge`. The Agent does not validate that certificate's chain; it extracts the raw Ed25519 public key and checks it against a heartbeat-pushed allowlist of currently active validators (`control-plane/internal/blockchainbridge/networkvalidatortls.go`; `provider-agent`'s `AllowlistClientCertVerifier`). `AGENT_SERVER_CA_FILE` (`/run/openinfra-tls/ca.crt`, the same dev CA every other service trusts) is the other direction: how this validator verifies an Agent's own TLS server certificate.

## Funding and registration

A freshly generated validator key starts at zero balance and cannot call `register_validator` (it reserves stake out of free balance) until funded. `deployments/scripts/bootstrap-network-validators.sh` runs at the end of `make dev-up`, after the stack is healthy: for each `networkvalidator*` service actually running, it funds the corresponding key from the Control Plane's own endowed bridge/sudo account (`controlplane-admin fund-account`, a plain `pallet_balances::transfer_allow_death`, no elevated origin needed) and then registers it (`networkvalidator register <stake>`, signed by the validator's own key, never sudo-wrapped) with `VALIDATOR_STAKE` (default `2000`, twice `MinValidatorStake`). The script is idempotent -- it checks `networkvalidator status` first and skips any validator already registered, so re-running `make dev-up` never re-funds or re-registers.

## Operations

```bash
make dev-up                                    # default: one networkvalidator
COMPOSE_PROFILES=multi-node make dev-up        # all three, quorum-capable

docker compose --env-file .env -f deployments/docker-compose.yml ps networkvalidator
docker compose --env-file .env -f deployments/docker-compose.yml logs -f networkvalidator

# Query a validator's own on-chain status directly:
(cd control-plane && \
  SUBSTRATE_RPC_URL=http://127.0.0.1:9944 \
  VALIDATOR_SIGNER_KEY_FILE=../deployments/local/validators/validator-key.pem \
  go run ./cmd/networkvalidator status)
```

The dashboard's validator views (`/dashboard/`) and `pallet-network-validator`'s own on-chain `Validators`/`Rounds` storage are the two ways to confirm a committee is actually running and closing rounds, rather than just registered and idle.

To add a fourth instance: extend the `for validator in ...` loop in `generate-dev-certs.sh` with a new key name, add a `networkvalidator-4` block in `docker-compose.yml` (profile `multi-node`, copying `networkvalidator-2`'s shape with a new `VALIDATOR_SIGNER_KEY_FILE`), and add its `service:key` pair to `bootstrap-network-validators.sh`'s loop.
